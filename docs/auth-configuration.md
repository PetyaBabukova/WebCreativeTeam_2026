# Настройки за администраторския вход

За локално разработване създайте `.env.local` в корена на проекта, до `package.json`. Файлът е игнориран от Git; операторът попълва стойностите лично, а агентите не го отварят. При Render задайте същите променливи в настройките на **новата** услуга. Не копирайте автоматично всички променливи от стария сайт. Собственият Express сървър и операторската команда зареждат локалните `.env*` файлове чрез `@next/env` преди auth настройките.

## Съпоставка със стария Render сайт

| Старо име | Нова настройка | Уточнение |
| --- | --- | --- |
| `DBLINK` | `AUTH_MONGODB_URI` | Може да се използва същият MongoDB клъстер, но новата auth база е отделна (`AUTH_DB_NAME`) и се предпочита потребител с права само за нея. Не се променя старата база. |
| `EMAIL` | `AUTH_SMTP_USER`, `AUTH_SMTP_FROM` | Само ако това е пълният Gmail адрес и е разрешен като подател. |
| `EMAIL_PASSWORD` | `AUTH_SMTP_PASSWORD` | Само ако е действаща Gmail app password за SMTP; попълва се лично, без копиране в Git или чат. |
| `EMAIL_SERVICE` = Gmail | `AUTH_SMTP_HOST`, `AUTH_SMTP_PORT` | Gmail SMTP: `smtp.gmail.com`, порт `465` с TLS. [Настройки на Google](https://support.google.com/a/answer/176600). |
| `NODE_ENV`, `PORT` | Системни настройки | Render ги задава за новата услуга; не се копират стойностите от стария сайт. |

Старите `SECRET`, `SESSION_SECRET` и `TOKEN_KEY` не се използват от новите сървърни сесии. CAPTCHA и PCloud настройките също не са част от администраторския вход. `SITE_URL` е HTTPS адресът на **новия** сайт, `AUTH_OUTBOX_KEY` е нов случаен 32-байтов ключ в Base64, а `AUTH_FIRST_ADMIN_EMAIL` е адресът, на който собственичката ще получи първата покана и с който ще влиза. `AUTH_SMTP_USER` е адресът на пощенския акаунт, който изпраща поканата. Те нямат пряк еквивалент в показания списък.

Не записвайте стойности в този документ, в Git или в чат. Задайте ги лично в secret manager на средата. Агентите проверяват само наличието и имената на променливите, без да отварят файлове с тайни.

## Задължителни за staging и production

| Име | Предназначение |
| --- | --- |
| `NODE_ENV` | `production` при production deployment. Auth отказва непознат или липсващ режим. |
| `SITE_URL` | Точният публичен HTTPS origin на **новия** сайт, без път и наклонена черта в края. Използва се за Origin проверка и имейл линкове. |
| `AUTH_MONGODB_URI` | MongoDB URI за отделната auth база на новия сайт; сървърът трябва да поддържа replica set транзакции. |
| `AUTH_DB_NAME` | Име на отделната auth база. Операторската команда отказва чужди колекции/липсващ маркер. |
| `AUTH_OUTBOX_KEY` | Случаен 32-байтов AES ключ в Base64, генериран и пазен само в secret manager. Не е паролата за MongoDB. |
| `AUTH_SMTP_HOST` | SMTP сървър на съществуващия доставчик. |
| `AUTH_SMTP_PORT` | SMTP порт. |
| `AUTH_SMTP_USER` | SMTP потребител. |
| `AUTH_SMTP_PASSWORD` | SMTP парола или app password. |
| `AUTH_SMTP_FROM` | Потвърден адрес на подателя. |
| `AUTH_FIRST_ADMIN_EMAIL` | Имейлът на първия администратор, който получава поканата и служи за вход. |

`AUTH_OUTBOX_KEY_ID` може да е кратък идентификатор за текущия ключ; по подразбиране е `v1`. При ротация задайте нов `AUTH_OUTBOX_KEY_ID` и ключ, а стария идентификатор/ключ временно чрез `AUTH_OUTBOX_PREVIOUS_KEY_ID` и `AUTH_OUTBOX_PREVIOUS_KEY`, докато старите чакащи писма бъдат доставени или изтекат. След това махнете предишния ключ. Не изтривайте чакащи писма като метод за ротация.

`AUTH_TRUSTED_PROXY_IPS` е незадължителен списък от **конкретни** IP адреси или CIDR мрежи, разделени със запетая. Попълва се само след като е известен действителният reverse proxy; празен списък означава, че `X-Forwarded-For` не се приема за доверен. Не задавайте мрежа, която включва произволни интернет клиенти.

За краткия staging период на CSP наблюдение задайте **само в staging услугата** `AUTH_DEPLOYMENT_STAGE=staging`, `AUTH_CSP_ENFORCE=0` и `AUTH_CSP_STAGING_ORIGIN`, равен на точния staging `SITE_URL`. Това изисква `NODE_ENV=production` и HTTPS origin. Ако настройките бъдат копирани към услуга с друг адрес, сървърът отказва старт. Сървърът запазва наложена защита срещу вграждане на страницата и изпраща пълната CSP като `Content-Security-Policy-Report-Only`. Предупрежденията се преглеждат в браузърната конзола при контролирани тестове; няма публичен endpoint за отчети. За реалния production сайт не задавайте `0`: при липсваща настройка пълната CSP се налага автоматично, дори ако `SITE_URL` е сгрешен. `AUTH_CSP_ENFORCE=1` принудително я налага и в локалните/E2E проверки. Staging настройката не променя HSTS, бисквитките или Origin проверката.

При Render Web Service `RENDER=true` и `RENDER_SERVICE_TYPE=web` се задават автоматично; приложението доверява само непосредствения Render proxy (един hop) за реалния клиентски IP. При друг хостинг задайте `AUTH_TRUSTED_PROXY_IPS` само след проверка на адресите на действителното proxy. Лимитите за вход ползват този IP. [Render: променливи на средата](https://render.com/docs/environment-variables), [Render: входящ трафик към web service](https://render.com/docs/web-services).

При безплатен Render Web Service изходящите SMTP портове 25, 465 и 587 са блокирани. За Gmail SMTP е необходим платен Render план или отделен доставчик с HTTPS API и съответна интеграция. [Render: ограничения на Free](https://render.com/docs/free).

## Операторски действия

След build и преди реална покана доверен оператор изпълнява `npm run auth:operator -- prepare` срещу потвърдената **нова** база. Командата проверява replica set, собствеността на базата и броя администратори, преди да създаде индексите. `npm run auth:operator -- check-count` е проверка на броя.

За първата покана операторът задава лично `AUTH_FIRST_ADMIN_EMAIL` и изпълнява `npm run auth:operator -- bootstrap`. Командата не изписва линка или токена. Писмото минава през шифрованата опашка и SMTP. Първоначалният собственик задава име за показване и нова парола; старите JWT/пароли не се импортират.

Аварийното `recover-owner` е само за доверен оператор след независима проверка на собственичката. Изисква `AUTH_RECOVERY_EMAIL`, `AUTH_RECOVERY_VERIFIED=yes-independent-verification` и при нужда `AUTH_COMPROMISED_ADMIN_IDS` като списък с потвърдени ID. Няма публичен recovery endpoint. Командата обезсилва паролата, сесиите и токените, а нов reset отива само до потвърдения адрес.

За автоматичните локални интеграционни тестове се ползва отделна временна replica set чрез `AUTH_TEST_MONGODB_URI`; тестовият пощенски транспорт работи само с `NODE_ENV=test`. Тестовата конфигурация не трябва да се използва в production.

## Проверка преди пускане

Този ред се изпълнява в отделна staging услуга и база, без достъп за запис до базите на стария сайт. Локалните автоматични тестове не заместват проверките през реалния HTTPS адрес.

1. Използвайте отделен staging origin, MongoDB потребител с права само за staging auth базата и контролирана тестова пощенска кутия. Задайте `NODE_ENV=production`, потвърдете, че URI сочи към replica set с TLS (`mongodb+srv://` или `tls=true`), `SITE_URL` е точният HTTPS origin, а `NODE_TLS_REJECT_UNAUTHORIZED` не е `0`. Проверявайте само имената и наличието на тайните; не ги извеждайте в логове.
2. Изпълнявайте операторските команди от отделната staging услуга с нейната собствена частна среда, а не от локален checkout със смесени `.env*` настройки. Потвърдете името `AUTH_DB_NAME`, преди да стартирате командата. След build изпълнете `npm run auth:operator -- prepare` и `npm run auth:operator -- check-count` **само** срещу staging базата. `prepare` създава auth индексите и маркера за собственост в новата база. Ако командата откаже заради чужди колекции, липсващ маркер или разминаване в броя администратори, спрете без изтриване и без заобикаляне на проверката.
3. С контролирана тестова пощенска кутия задайте `AUTH_FIRST_ADMIN_EMAIL` и изпълнете `npm run auth:operator -- bootstrap`. Проверете покана → приемане → вход → изход, покана на втори администратор, отмяна на покана, забравена парола, смяна на парола и имейл, деактивиране и възстановяване. Проверете `recover-owner` само върху тестови акаунти след независима проверка. Потвърдете, че двата администратора могат да работят едновременно от различни устройства и че старите сесии се обезсилват при промяна на парола.
4. През публичния адрес проверете `Secure`, `HttpOnly`, `SameSite=Lax` и `__Host-` за сесийната бисквитка, `no-store` за auth отговорите, липса на кеширане от CDN, точен клиентски IP зад proxy, действащи лимити и HSTS. При staging наблюдение проверете наложената базова CSP и пълната `Content-Security-Policy-Report-Only`, после прегледайте предупрежденията в браузърната конзола на публичните и административните страници. Не допускайте пароли, сурови токени, линкове за възстановяване или SMTP данни в HTML и логовете.
5. Измерете p95 за `/api/auth/status` и защитените auth маршрути, броя DB операции и допълнителната заявка на хедъра при реалния staging трафик. Измерете Argon2id при ресурсните лимити и паралелизма на staging услугата, преди да приемете окончателни стойности. Проверете доставянето и повторните опити на SMTP, включително временно недостъпен доставчик.
6. Преди production cutover премахнете `AUTH_CSP_ENFORCE=0` и проверете автоматично през публичния адрес, че HTML страница, auth API и страница за грешка връщат пълна `Content-Security-Policy` без `Content-Security-Policy-Report-Only`; проверете и че proxy/CDN не връща стари заглавки. Потвърдете отделния DB потребител, replica set транзакциите, `adminControl.activeCount`, outbox ключа, trusted proxy настройката, имейл транспорта, сроковете за audit и изтриване, HTTPS и липсата на test mail transport. Запазете предишния deployment artifact за rollback. Старият сайт продължава да работи самостоятелно; новите auth колекции не се изтриват автоматично при rollback.

Текущият HSTS срок е една година; staging адресът не бива да се използва впоследствие за HTTP. CSP наблюдението използва само тестови акаунти и пощенски кутии.

## Приети срокове и политика

Неактивна сесия: 12 часа. Абсолютен срок: 2 дни от входа, включително за вече издадени сесии. Покана: 48 часа. Reset: 30 минути. Audit журнал: 90 дни с TTL; записи без пароли, сурови токени или пълни IP адреси. Окончателното изтриване на личните данни за **деактивиран** администратор е отделно действие след повторна парола и изписване на точния имейл. Първоначалният собственик не може да бъде изтрит с обикновения поток, защото стабилният `ownerUserId` е нужен за аварийно възстановяване.
