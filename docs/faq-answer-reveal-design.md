# FAQ card opening motion

## Brief

Opening an FAQ card should feel smooth rather than flash. The previous idea of orange rules beside the questions was rejected by the user and is out of scope. Preserve the existing three desktop rows, mobile list, single open card, hover and click behavior, and card artwork.

## Current behavior and cause

- `FaqCard` in `components/FaqPage.tsx` uses Motion to animate desktop `flexGrow` over 0.62 seconds. Its front-loaded easing makes most of the change happen early. Motion also animates answer height and top margin.
- The `.faq__card--open` CSS class immediately replaces the card's transparent dark background with an opaque cream image background, changes its border color, and changes inherited question text from white to dark. This instant visual change while width is still moving is the likely source of the reported flash.
- Desktop answer opacity has a separate 0.65 second delay, so text appears only after most of the expansion. That delay also applies when reduced motion is requested. The earlier Opus-reviewed answer-timing proposal remains relevant and is incorporated here.

## Proposed change

1. Keep the closed card's dark transparent base. In the existing `FaqCard`, add one decorative `motion.span` first in the article, with the existing `--faq-card-art` image and cream base. Give the card `isolation: isolate`, and the span `position: absolute; inset: 0; z-index: -1; border-radius: inherit; pointer-events: none`, `aria-hidden="true"`, and `initial={false}`. This places the light surface above the card base and below all content. Animate its opacity between zero and one over 0.32 seconds using Motion ease-in-out; on mobile close, use 0.12 seconds because the answer height already collapses immediately. Remove the instant background swap from `.faq__card--open`.
2. Animate the article's `borderColor` alongside the surface over 0.32 seconds. Animate the `<article>` color separately; the question button inherits it while the answer and number retain their own colors. On desktop opening and closing, hold the current color for about 0.105 seconds, then change it over 0.045 seconds as the surface crosses its midpoint. On mobile close, change the color over 0.035 seconds without delay. This brief transition avoids a prolonged low-contrast mid-tone question. The first 0.18-second hold and 0.12-second color tween suggested in the initial review proved too slow when intermediate browser frames were inspected: the surface was already almost cream while the question was still grey. Remove instant border and text color changes from `.faq__card--open`.
3. Use a gentler Motion ease-in-out tween for desktop `flexGrow`, answer height, and answer top margin, lasting 0.68 seconds. Derive the desktop hover lock from that shared duration plus 80 milliseconds, so hovering a neighboring card cannot interrupt the last frames. Keep the current mobile height duration and scroll anchoring. Do not use a spring: it could overshoot and make neighboring cards shake.
4. Start the desktop answer opacity fade after about 0.2 seconds, once the light surface is mostly visible, and let it finish over 0.4 seconds. This reveals the answer while the card is still expanding, without making partly clipped text fully opaque. Apply the same start on mobile open but keep its 0.28 second fade, where the card width does not change. When reduced motion is requested, set all new transitions and the answer delay to zero; `MotionConfig reducedMotion="user"` does not automatically disable opacity, color, or `flexGrow` animation.
5. Keep one palette object in `FaqPage.tsx` for the existing closed/open text and border colors and the cream surface color. Feed those values to Motion targets and CSS custom properties on the existing FAQ page root, avoiding duplicated color literals across TypeScript and CSS. Keep closed colors in CSS through those custom properties for server rendering. Use the open class for state, answer visibility, and accessible button attributes.
6. In forced-colors mode, hide the decorative layer and set `color: CanvasText !important; border-color: CanvasText !important` on the card. In print, hide the layer and set `color: black !important; border-color: #ccc !important` on the card, overriding Motion's inline values. Preserve the current no-JavaScript answer fallback. Its pre-existing grey-on-dark answer contrast is outside this motion change.

## Verification

- On desktop, open a card by hover and by click; inspect the start, middle, and end of the transition. The light artwork and staged question color should change gradually while the card grows, with no abrupt flash or noticeable low-contrast interval. The answer should begin appearing during expansion. Any brief right-edge clipping of the growing answer should be faint. Watch for distracting artwork zoom caused by `background-size: cover` while card dimensions change; keep `cover` only if it looks stable across narrow and wide desktops.
- Switch between cards. The previous card should fade to dark while the new card fades to light, with only one open answer. Confirm the longest answers fit at the narrowest desktop width and that the three rows retain their existing layout.
- On mobile, tap two questions in sequence. Confirm the background crossfade is smooth, the tapped answer stays open, and scroll position does not jump. Confirm tablet layout also works.
- Check reduced-motion, keyboard focus, forced-colors, print, and no-JavaScript rendering. Run the existing FAQ browser tests, build, and lint. Add a focused browser check for the final open/closed surface opacity and question colors, plus a print-media check for black text and hidden artwork; use manual frame inspection for subjective transition quality.

## Scope and risk

Reuse `FaqCard`, its CSS file, and the installed Motion library. One small decorative child is needed because CSS background images cannot be interpolated as a card expands. The main risks are low text contrast at the transition midpoint, artwork zoom from `cover`, and a lingering light compact card on mobile close. Staged text color, visual frame checks, and a faster mobile close address them. The current card geometry, artwork, copy, and other pages remain unchanged.

## Review and decision

The earlier version of this document was reviewed by Claude Opus on 2026-10-15 for the answer delay and per-card orange rules. It identified the reduced-motion delay and potential clipping during width growth. The user rejected the orange rules after implementation; they were removed.

Opus reviewed the first version of this opening-motion proposal. It identified that an ordinary absolute layer would cover content, synchronized text/background interpolation would create low contrast, and the answer would appear before the light surface was readable. We adopt an isolated layer behind content, staged text color, and an answer fade beginning about 0.2 seconds into the 0.68 second expansion. We also adopt explicit print/forced-colors overrides, a duration-based hover lock, and a fast mobile closing fade. We keep `background-size: cover` initially because the card dimensions vary widely; visual inspection will decide whether its zoom is acceptable. The palette will have one source in the component and feed CSS custom properties to prevent color drift.

In the follow-up review, Opus confirmed the approach and flagged ambiguous wording for the closing text color. The article owns the inherited question color, and the hover lock is 80 milliseconds longer than the layout transition. Browser frame samples showed surface opacity around 0.5 at 0.11 seconds and above 0.9 by 0.22 seconds. A 0.18-second hold followed by a 0.12-second tween left grey text on an almost-white card; we moved the brief color change to the surface midpoint in both directions. This retains the review's contrast goal while removing the observed low-contrast interval.

Opus also reviewed the implementation diff. It found no correctness bug but flagged possible answer clipping during width growth. Frame measurements at 1280px showed the clipping fall to about 16px at 0.60 answer opacity, then disappear before full opacity. We lengthen only the desktop answer fade to 0.4 seconds; it still begins at 0.2 seconds, so the answer is visible during expansion. Reduced-motion, forced-colors, and mobile-close checks are added to the verification.
