## 1. Цел и граници

Изграждаме нов сайт в това репо. Текущият публичен сайт продължава да работи до отделно одобрена миграция. Преизползваме подходящите интеграции и проверена логика от стария проект след преглед; не копираме автоматично цялата му архитектура.

Производителността, достъпността и SEO са задължителни. Съдържанието, навигацията и основните действия не зависят от WebGL или анимации. Сайтът трябва да изглежда завършен и при изключени ефекти.

Този документ описва архитектура и последователност на работа. Не създаваме приложение, зависимости или услуги преди техническото ревю и одобрението на потребителя.

## 4. Една Render услуга и разделени отговорности

Предложение: един Node процес с Express като custom server, който стартира Next програмно и предава към него всички заявки за страниците и Next ресурсите.

```text
Браузър → HTTPS домейн → една Render Web Service
                           └─ Node / Express
                              ├─ /api/* → controllers → managers → MongoDB / интеграции
                              ├─ /healthz → минимална проверка за готовност
                              └─ останалите заявки → Next request handler
                                                     ├─ App Router / SSR
                                                     ├─ статични ресурси
                                                     └─ image optimization
```

Това е една хостинг услуга и един публичен порт. Atlas, мейлът и storage са външни зависимости, а не допълнителни Render Web Services. Техните лимити/цени се оценяват отделно; не обещаваме нулева цена за неограничена медия.

### Стартиране и build

- Един коренов `package.json` и lockfile са достатъчни. Не е нужен монорепо инструмент за две части на едно приложение.
- План за build: `npm ci` → `npm run build`, като build изгражда Next и компилира Express TypeScript в отделен server output.
- Express има отделна TypeScript build конфигурация, която не наследява Next `noEmit`/bundler настройки без проверка. Node module форматът и резолюцията на imports се проверяват при production старт; генерираният server output не се включва повторно в Next compilation.
- `npm start` стартира компилирания custom server, а не `next start`. Next build сам не компилира custom server кода.
- Процесът слуша на `0.0.0.0` и Render `PORT`. `NODE_ENV=production` се задава в средата; scripts трябва да работят и на Windows.
- Подготовката на Next и връзката към MongoDB приключват преди приложението да обяви готовност. Грешка при старт прекратява процеса с неуспешен код.
- При спиране приключваме приема на нови заявки и затваряме HTTP и MongoDB ресурсите в ограничен срок. Логовете не съдържат тайни, сесийни идентификатори или съдържание на контактни съобщения.
- API parsing/валидация се монтира само върху Express API маршрутите. Не консумираме request body преди Next handler, включително при Next вътрешни заявки.
- Неизвестен `/api/*` връща API 404; не пада към HTML страницата на Next. API има собствен error handler.
- Конфигурацията за trusted proxy, secure cookies и IP rate limits се проверява срещу реалния Render proxy път; не се доверяваме безусловно на произволни forwarded headers.

### Ограничения и задължителна проверка

Custom server е поддържан механизъм, но се различава от стандартния Next старт. Не използваме `output: standalone` с него. Сървърният output трябва да включва действително необходимите файлове и зависимости.

След одобрение първата техническа проверка е production build/start: SSR, streaming, Next assets, image optimization, suffix routing, 404, cookies и рестарт в една услуга. Ако има конкретна несъвместимост, обсъждаме корекцията преди изграждането на останалия сайт. Не преминаваме мълчаливо към две платени услуги.

Двата слоя споделят CPU/RAM и общ рестарт. Следим реалната памет и времето за отговор, особено при image optimization; една услуга не означава неограничен капацитет. 3D рендирането се извършва в браузъра.

## 5. Собственост на логиката и ориентировъчна структура

```text
app/                 Next layouts, pages, metadata, error/loading/not-found
components/          UI компоненти и техните специфични CSS Modules
styles/globals.css   общата дизайн система и базови стилове
messages/            bg/en преводи на интерфейса и статичните текстове
lib/                 само нужните Next/server adapters и чисти общи функции
server/
  controllers/       Express routers: заявка → manager → HTTP отговор
  managers/          бизнес логика и операции с данните
  models/            MongoDB/Mongoose схеми
  middleware/        auth, authorization, validation, errors, rate limits
  helpers/           конкретни помощни функции и интеграции
  index.ts           custom server entry point
public/              одобрени статични ресурси, лого, fallback изображения
tests/               необходимите интеграционни и browser проверки
```

Това е карта на отговорностите, не списък за автоматично генериране на празни файлове. Преди нов компонент/helper се търси вече съществуващ. Нова абстракция се добавя само при реална нужда.

- Controllers са Express routers, както е поискано. Те извличат валидираните аргументи, извикват manager и определят HTTP отговора.
- Managers не приемат `req`/`res`. Те държат единствената имплементация на бизнес правилата и заявките.
- Всички бизнес mutations и публични API endpoints са в Express. Не създаваме паралелен CRUD в `app/api` или Server Actions.
- Server Components могат да използват тесен server-only read adapter към същите managers. Така SSR и build не зависят от HTTP заявка към собствения още нестартирал сървър. Adapter-ът не дублира бизнес правила и не се импортира от Client Components.
- Next adapter-ът има `import 'server-only'` като build защита. Самият общ manager не импортира Next-specific sentinel/runtime, защото се използва и от обикновен Node/Express. Mongo connection/model initialization е идемпотентна и безопасна при Next bundling и dev reload; reuse на връзка не зависи само от module-local флаг.
- Публичните read функции връщат само публикувани записи и изрично подбрани полета. Административните reads изискват проверена сесия; UI скриване не е авторизация.
- Next handler се добавя само за реална Next runtime необходимост, например бъдеща revalidation, с отделна защита и без повторна бизнес логика.

## 6. Езици, маршрути и метаданни

### Публичен договор

Примери, а не финална навигация:

```text
/bg                         /en
/about/bg                   /about/en
/services/bg                /services/en
/blog/<slug>/bg             /blog/<translated-slug>/en
```

Валидните езици са само `bg` и `en`. Неизвестна страница или език връща истински 404. Статичните slug-ове засега могат да са общи; окончателните имена и миграционната карта се уточняват преди съдържанието.

### Вътрешна организация

Предлагаме общ locale root layout в `app/(site)/[lang]/layout.tsx`, с `rewrites` в `next.config`, които вътрешно преобразуват публичните suffix URL-и. Например `/about/bg` се обслужва от вътрешното `/bg/about`, без да сменя видимия адрес. Това запазва едно място за езиковия layout и `<html lang>`. Admin има root layout в `app/(admin)/layout.tsx` и страници под `app/(admin)/admin/...`; route groups не добавят URL сегменти. Няма общ `app/layout.tsx`, който да дублира `<html>`.

- Нормализацията се реализира чрез ограничени `next.config` rewrites (при нужда `beforeFiles`) и съответните canonical `redirects`, от една обща карта на маршрутите. Не зависи от `middleware.ts`/`proxy.ts` и не се дублира в Express. Не твърдим, че custom server универсално изключва Next middleware; проверяваме действителното поведение на фиксираната версия.
- Разпознаваме само одобрени публични маршрути. Изключваме `/api`, `/admin`, `/healthz`, `/_next`, файлове и metadata routes.
- Директно отворен вътрешен prefix адрес се пренасочва постоянно към публичния suffix адрес. Вътрешният rewrite не трябва да се пренасочва обратно в цикъл.
- Всички Link адреси, canonical, hreflang, sitemap и OG URL-и използват само публичната форма. Те не се извеждат наивно от вътрешния pathname.
- Това е задължителен договор: един общ URL builder използва идентификатор на маршрута, slug и език. `usePathname` не е източник на canonical адреси; поведението при server/client rendering и rewrites се тества за hydration несъответствия и правилно активно меню, без предположение, че винаги връща една и съща форма.
- Проверяваме hard reload, client navigation, prefetch, RSC заявки и 404 на production build. Ако routing подходът не покрива тези проверки, преминаваме към директни suffix route файлове с общи компоненти, запазвайки публичните адреси.
- Locale layout задава точния `html lang`. Не използваме едновременно два вложени root `html` layout-а. Admin има собствен отделен layout; сменянето на root layout може да доведе до пълна навигация.

Езикът в URL винаги има предимство пред запомнено предпочитание. Предложен начален default за `/` е `/bg`, подлежащ на потвърждение. Не е нужна cookie за език на първия етап; ако добавим запомняне, не използваме localStorage за сървърно определяне на езика.

Преводите на статичния интерфейс са в `messages`. Редактиращото се съдържание е в базата с езикови варианти и стабилен общ идентификатор. Language switcher отваря съответния превод, дори slug-ът да е различен. Непубликуван/липсващ превод не се рекламира чрез hreflang или sitemap и не се замества тихо с друг език.

Всяка публикувана страница има локализирани title/description, self-canonical, наличните взаимни hreflang връзки, OG данни и приложим JSON-LD. `sitemap` и `robots` се генерират чрез Next metadata conventions, не като дублирани Express ресурси. Admin и preview не се индексират; реалната защита е автентикацията.

## 7. Данни, CMS и кеширане

До двама администратори управляват съдържание през собствен малък интерфейс. Предлагаме публикации с чернова/публикуване, проекти при потвърждение на секцията и редакция на определени полета на страниците. Не изграждаме произволен page builder.

- Схемите определят позволените полета, ограниченията, езиковите slug-ове, статусите и timestamps. Уникални индекси пазят необходимите комбинации от език и slug.
- Публичните заявки филтрират публикационния статус на сървъра. Пагинацията има горна граница; филтри, sort и update полета са allowlisted. Не подаваме директно request обекти към Mongoose.
- Rich text редакторът и форматът се избират преди блог имплементацията. Съдържанието се валидира и sanitise-ва с allowlist; произволен HTML/скриптове не са разрешени.
- Редактиращите се картинки имат storage key, размери, тип и локализиран alt текст. Не пазим големи бинарни медии в MongoDB.
- Разработката използва отделна база/потребител с ограничени права. Не пишем в live базата по време на новия build. Схемите и пренасянето на данните минават през отделен миграционен план.

Начална стратегия за свежест: DB-driven публичните страници се рендират сървърно при заявка, без persistent Next data/full-route cache за тези данни. Преди DB read се задава изрична request-time граница, например `await connection()` за съвместима Next версия, или `dynamic = 'force-dynamic'` при съответния caching режим. Избираме един проверен подход при фиксиране на версията; не смесваме несъвместими настройки с Cache Components. Директна Mongoose заявка сама по себе си НЕ гарантира динамично рендиране. Метаданни и DB-driven sitemap също трябва да имат проверена свежест; sitemap може да използва изрично динамичен route segment при избрания режим. Не активираме допълнителен shared/CDN cache за HTML по подразбиране. Статичните ресурси използват нормалното си кеширане.

Това избягва преждевременно добавяне на revalidation endpoint. След публикуване нова заявка трябва да показва новото съдържание; административният интерфейс refresh-ва своя изглед. Вече отворен публичен таб не получава автоматични live updates. Проверяваме и поведението на клиентския router cache.

Ако реалните измервания покажат нужда от ISR/данни с TTL, добавяме отделно описана стратегия: ключове по език/ресурс, инвалидиране след успешна mutation, защитена Next runtime граница и тест за publish/unpublish/delete. Не маркираме admin, preview и session отговори като публично кешируеми.

## 8. Вход, контактна форма и интеграции

Предложение за admin: сървърни сесии с Mongo-backed session store и cookie `HttpOnly`, `Secure` в production и `SameSite=Lax`. Няма публична регистрация. Сесиите имат срок, отмяна при logout и ротация при login; няма tokens в localStorage. Паролите се хешират с утвърден password hashing механизъм.

Express и Next SSR използват една server-side проверка на сесията и един store, а не два независими механизма. Next adapter чете cookie през `cookies()`, проверява подписа/формата чрез общия session helper, търси валидната сесия и актуалните права и едва тогава извиква admin manager. Ако се използва `express-session`, неговият подписан cookie формат се проверява със същите правила и secrets; суровата cookie стойност не се приема направо като доверен session id. Отхвърляме изтекла/отменена сесия независимо кога Mongo TTL cleanup физически ще изтрие документа.

Начално сесиите имат абсолютен срок без rolling renewal от Server Components. Login/logout/ротация и cookie writes са собственост на Express. Next SSR проверката е read-only и не разчита на `req.session`, прикачен от Express. Защитата се изпълнява във всеки server-side достъп до admin данни, не само в layout, който може да се преизползва при навигация. Резултатите от auth не се кешират между потребители.

Всички административни API reads/mutations проверяват автентикация и права. За mutations има CSRF защита и проверка на Origin; SameSite не е единствената защита. Login и контактната форма имат rate limits, ограничени request размери и безопасни съобщения за грешки. В началото може да има process-local rate limiter за една инстанция, с изрично приет reset при рестарт; той не замества CAPTCHA или валидирането.

CSRF доставката използва същия Express auth router: same-origin, non-cacheable endpoint издава token, обвързан със сесията, включително кратка pre-login сесия. Admin клиентът подава token в header при login/logout и mutations; Express го проверява заедно с Origin. При login session id и token се сменят. Endpoint-ът не се отваря с permissive CORS и не се реализира втори път в Next.

Мейлът, templates и CAPTCHA се проучват в стария проект без четене/печат на secret-bearing env файлове. Запазваме доставчика и работещите настройки, когато са съвместими. Невидима CAPTCHA не означава непременно v3. Не задаваме score праг преди да установим версията и сегашното поведение. Изразът „с 300 зора“ не е технически параметър.

Контактната форма валидира входа на сървъра, проверява CAPTCHA, предотвратява header injection и има ограничено чакане към доставчика. Показва успех само при прието изпращане; при timeout/неясен резултат избягва автоматично повторение, което може да дублира съобщението. Изпращачът е проверен адрес, а посетителският адрес се ползва само като валидиран Reply-To.

## 9. Storage и видео

Изборът на нов storage е отворен. Кандидати: Cloudinary за готови медийни трансформации или Cloudflare R2 за object storage. Оценяваме обем на снимки/видео, трафик, обработка, цена и удобство преди uploads имплементацията. Това не блокира архитектурното ревю или локалните статични ресурси.

- Качените през admin файлове не се съхраняват трайно върху обикновената Render файлова система.
- При подписан direct upload Express първо проверява сесия/CSRF и разрешения размер/тип; завършването се проверява на сървъра преди запис в MongoDB. Клиентът не може да регистрира произволен чужд storage key.
- Проверяваме действителния файлов тип и размер, не само разширението. Произволни SVG/HTML uploads не се допускат. Собственото проверено SVG лого е статичен репо ресурс.
- Подмяна на медия първо качва/валидира новия ресурс и записва успешната промяна; старият файл се изтрива само ако вече не се използва. Предвиждаме почистване на неуспешни/осиротели uploads и възстановяване от backup.
- Само разрешените storage host/path комбинации се включват в Next image конфигурацията.

Потребителят създава евентуалните cinematic видеа в Kling. Те са за отделни секции, с poster, подходящи WebM/MP4 варианти, `muted`, `playsInline` и без ненужна аудиописта. Зареждат се близо до видимата секция и спират извън нея. Същественото съдържание остава в HTML. Видео с информационно аудио би изисквало отделно решение за субтитри/транскрипция.

## 10. Глобална стилизация и дизайн

`styles/globals.css` е единният източник за цветови tokens, шрифтове, размери, spacing, containers, grids, типография, бутони, форми и повтарящи се варианти. Не дублираме същите variables в друг файл.

CSS Modules съдържат само специфичната композиция и изключенията на компонента. Общ компонент Button не изисква отделна копия на button styles. Използваме общи класове за визуалните варианти, а не тежки правила върху всеки гол `button`, включително иконни контроли. Focus, disabled, error и hover състояния са част от общите правила.

Палитрата се уточнява с потребителя. SVG логото съдържа оранжево `#EF7F1A` и зелено `#749728`; това са изходни бранд стойности, а не автоматично одобрени цветове за всички текстове/бутони. Контрастните UI варианти могат да са различни. Не фиксираме HEX стойностите, измислени в стария план.

Шрифтът трябва да има качествена българска кирилица и нужните латински начертания. Зарежда се локално чрез подходящата Next font интеграция, с ограничени тежести. Размерите са responsive; дизайнът се проверява с реалните BG/EN текстове, не само с кратки placeholders.

Мокъпите от `2026_Redesign/` и Clay/KOTA/Refokus са визуални ориентири. Не възпроизвеждаме цяла картинка като сайт. Реалните медии, навигацията, редът на секциите и позиционирането на услугите остават за одобрение.

## 11. Hero и движение

Първият отговор съдържа четим HTML текст, CTA и оптимизирания статичен poster. Hero poster се зарежда приоритетно, а не lazy; зададени са размери и responsive variants. Останалите изображения могат да са lazy според видимостта.

Three.js кодът и ресурсите се зареждат отделно след критичното съдържание и само когато интерактивният вариант е подходящ. Dynamic import сам по себе си не гарантира късно зареждане. Преминаването от poster към сцената става след готов първи кадър, без промяна в layout.

Сцената има един основен стъклен/органичен обект, ограничени светлинни ефекти и деликатна реакция на курсора. Геометрията, материалите и environment ресурсите се подготвят специално; библиотеката не гарантира автоматично вида на AI мокъпа. Плаващите UI панели са HTML/CSS.

На телефон използваме по-проста композиция и по-ниска графична тежест. Ограничаваме pixel ratio, текстури, прозрачни слоеве и частици; не определяме качеството само по ширината на екрана. Реални измервания и capability checks определят fallback. При WebGL грешка/context loss или изключен JS остава статичният вариант.

Рендер цикълът и декоративните анимации спират при невидим таб/hero; ресурсите и listeners се освобождават при unmount. Въртенето на hero кълбото пази достигнатия ъгъл при пауза и при излизане от екрана и продължава от него при връщане.

**Решение на потребителя, 30 септември 2026 г.:** входната Motion последователност, въртенето и наклонът при мишка се изпълняват еднакво за всички посетители, независимо от системното `prefers-reduced-motion`. Част от Windows посетителите изключват „Animation effects“ за производителност и така досега изобщо не виждаха ефектите. Потребителят управлява продължителното въртене с малък, достъпен с клавиатура бутон за пауза/пускане. Това решение се отнася за текущата hero сцена; бъдещите сцени получават отделен дизайн и преглед.

Текстовата последователност е предложение, не финален copy. Появата не задържа достъпа до CTA и след приключване оставя четимо послание. SVG logo intro е кратко и не блокира навигацията. Няма задължителен preloader, scroll-jacking или непрекъснато въртящ се важен текст.

## 12. Достъпност, производителност и защита

Цел: WCAG 2.2 AA за приложимите критерии. По решение на потребителя от 30 септември 2026 г. hero анимациите не зависят от `prefers-reduced-motion`. WCAG 2.3.3 „Animation from Interactions“ е AAA; целта AA включва 2.2.2 „Pause, Stop, Hide“ (ниво A) за приложимото автоматично продължително движение. Автоматичен audit сам не доказва съответствие.

- Семантична структура, правилни headings/labels, keyboard navigation, видим focus, skip link и достъпни грешки във формите.
- Контрастът се проверява върху действителните фонове, включително glass panels. Нормален текст минимум 4.5:1; голям текст минимум 3:1; приложимите UI граници и focus индикации също се проверяват.
- Информацията не се предава единствено чрез цвят или canvas. Чисто декоративната графика се скрива от assistive technologies.
- Продължителното въртене на hero кълбото има видим бутон за пауза/пускане с `aria-pressed`, BG/EN етикети и управление с клавиатура. Паузата замразява текущия ъгъл; входната последователност завършва сама. Бутонът е достъпен и за посетители със системно намалено движение.
- Проверяваме reflow, увеличение, touch targets и реална клавиатура на BG/EN версии.

Цели за Core Web Vitals на 75-ия персентил: LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1. Лабораторните измервания са предварителна проверка; полевите данни потвърждават резултата след достатъчно посещения. Не използваме FID/TTI като текущи основни критерии.

Преди пълната hero имплементация записваме отделни бюджети за initial JS, deferred 3D JS, модели/текстури, poster и видео след baseline build и прототип. Не обещаваме общ размер от 200 KB с 500 KB изключения. Тестваме и реален телефон със среден клас хардуер; при неизпълнен бюджет опростяваме ефекта.

Security headers и CSP се настройват спрямо избрания Next runtime, CAPTCHA и медийни домейни. Политиката се проверява, без да се разрешават произволни източници за удобство. Валидацията, CSRF и session защитата остават в бекенда.

При nonce CSP уникалният nonce трябва да стигне както до Next request/render контекста, така и до response CSP, преди Next да изпрати headers. Само response header от Express не е достатъчен. Изборът между тествана nonce интеграция и подходяща hash/static политика е част от първия production spike; проверяваме hydration, CAPTCHA и image/media източниците, без автоматично отслабване с широки wildcard разрешения.

Analytics не е автоматично изискване. Изборът, consent поведението и необходимите текстове за поверителност се решават отделно. Не твърдим, че „без cookies“ или localStorage автоматично означава правно съответствие.

## 13. Проверки и ред на реализация

След одобрение работим на малки етапи:

1. Преглед на старите интеграции и съществуващите URL-и, без секрети; избор на версии.
2. Минимален skeleton и доказване на single-service production старта, suffix routing и езиковите layouts.
3. Глобална дизайн система и малък hero прототип с реални измервания; одобрение на визуалната посока.
4. Модели, сесии и минимален admin; избор на storage преди uploads.
5. Одобрени страници/съдържание, BG/EN метаданни, контактна форма и медия.
6. Интеграционни/browser проверки, performance/accessibility преглед и миграционна репетиция.
7. Отделно одобрение за production подмяната и план за rollback.

Задължителни проверки според реално реализираната функционалност:

- Production build/start, ready/failed startup, API 404, Next resources и image optimization.
- Suffix URL hard reload/client navigation/prefetch, prefix canonical redirects без loop, валиден `html lang`, липсващ език/превод и реални 404.
- Login/logout/session expiry, отказ при липса на права/CSRF, недостъпни чернови, безопасно rich text съдържание.
- Една валидна/подправена/изтекла/отменена сесия дава същия резултат в Express API и Next SSR, включително директен URL, RSC/prefetch и навигация. Logout отнема достъпа при следваща server заявка.
- Publish/unpublish/delete се отразяват в страниците, sitemap и language links според стратегията за свежест.
- Контактна форма: валиден/невалиден вход, CAPTCHA failure, rate limit и mail failure.
- Upload: отказ при неразрешен тип/размер/чужд key, подмяна и неуспешен запис без загуба на ползваната медия.
- BG/EN mobile/desktop, keyboard, reduced motion, изключен JS, WebGL failure и липса на layout jump.

Не пишем тестове, които само повтарят CSS стойности. Точният test runner се избира със scaffolding; browser smoke проверки и тестове на сигурността/данните са приоритет. CI изпълнява typecheck, lint, приложимите тестове с coverage проверка и production build. Не е необходим пълен CMS dataset за build: DB-driven pages са динамични и build не трябва да прави live writes или да разчита на работещ собствен HTTP API.

### Задължително тестово покритие — добавено на 28 септември 2026 г.

Изискване на потребителя: минимум **80% тестово покритие**. За измерим и еднозначен критерий залагаме минимум 80% по всеки от показателите **lines, statements, functions и branches**, отделно за фронтенд и бекенд. Високото покритие на единия слой не компенсира ниско покритие на другия.

- Coverage конфигурацията се добавя още при началната настройка. Включва целия приложим собствен изпълним TypeScript/JavaScript код, включително файловете, които никой тест не импортира.
- Изключват се зависимости, генериран код/build output, декларации само за типове, самите тестове и тестовите им помощни файлове, статични ресурси и конфигурация без приложна логика. Не изключваме controllers, managers, middleware, UI логика или трудни за тестване файлове само за достигане на процента.
- CI приключва неуспешно при показател под прага в който и да е слой и запазва coverage отчета. Не намаляваме праговете и не разширяваме изключенията, за да прикрием регресия.
- Тестовете проверяват поведение, грешки и гранични случаи. Покритието не заменя задължителните проверки на авторизация, сесии, CSRF, публикуване, маршрути и интеграции, описани по-горе.
- Browser/E2E проверките остават отделно задължение; не ги броим автоматично към unit/integration coverage без действително събрано и коректно обединено покритие.

Това допълнение е ново изискване след Opus ревюто на версия 2.1; не е част от вече прегледания тогава текст.

## 14. Миграция и експлоатация

Преди смяна на live версията: карта стар URL → нов URL, запазване на подходящите адреси, постоянни redirects за променените и проверка за chains/loops. Запазването само на slug при нов езиков сегмент не запазва стария URL.

Проверяваме съдържание, canonical/hreflang/sitemap, robots, изображения, мейл, CAPTCHA domain configuration и стари вътрешни/външни връзки. Тестовият сайт не трябва да се индексира. Миграцията има backup на данни/медия, проверена възможност за restore и описан rollback към стария deploy с неговата съвместима база.

Деплой с ново репо/команди към съществуващата Render услуга се уточнява след преглед на реалната конфигурация. Не променяме услугата, DNS или live базата по време на архитектурното планиране. Не обещаваме, че само смяната на repo URL завършва миграцията.

### Финален контролен преглед — Claude Opus 4.8

Вердикт: планът е архитектурно съгласуван, без съществени архитектурни блокери, и е годен за одобрение с условие за планираната production проверка. Opus потвърди механизмите за общ build/start, разделението на логиката, suffix routing, динамичните reads и споделената сесия/CSRF.
